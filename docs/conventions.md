# Conventions
## Git
1. Workflow: [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)
1. Branch naming:
	* `main`,
	* `feature/{issue_id}-{kebab-case-name}`
	* `bugfix/{issue_id}-{kebab-case-name}`
1. Commit messages:
	* [Conventional commits](https://www.conventionalcommits.org/)
	* Past tense

## Releasing
Pushes to `main` never publish. The CI workflow only builds, tests and uploads a `X.Y.Z-ci.N` package as a workflow artifact.

1. **Draft:** Actions → *Draft release* → *Run workflow* on `main`. It calculates the next version, builds and tests,
   and creates a **draft** GitHub Release with notes generated by [git-cliff](https://git-cliff.org/) (`cliff.toml`).
   No tag is created yet; deleting the draft leaves nothing behind.
1. **Review:** edit the notes of the draft in the GitHub UI.
1. **Publish:** *Publish release* creates the tag `vX.Y.Z` and triggers the *Publish* workflow, which packs that
   version, pushes it to NuGet and attaches the `.nupkg`/`.snupkg` to the release.

Version:
* Calculated from the commits since the last `v*` tag: `!` or a `BREAKING CHANGE:` footer bumps major, `feat` bumps
  minor, anything else bumps patch.
* To override it, enter a version (e.g. `3.0.0`) in the *version* input when running *Draft release*.
* Pre-release: enter e.g. `3.0.0-rc.1`. The draft is marked as a pre-release automatically. The notes of the final
  `3.0.0` then list only the commits after `v3.0.0-rc.1`; merge the notes of the release candidates when editing it.

Release notes list only `feat`, `fix`, `perf` and breaking commits. `docs:`, `chore:` (including dependency bumps),
`test:`, `ci:`, `build:`, `style:` and `refactor:` commits never appear, and neither do PR merge commits unless they
are marked breaking. Preview the notes locally with `git cliff --unreleased --strip all`.

## C#
1. Source code
	* [Guidelines](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/)
	* Indent character: *space*.
	* Constant naming style: *PascalCase*.
2. Tests
	* [Naming convention](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices#naming-your-tests)
	* Types: unit, integration, functional, guard (convention).
